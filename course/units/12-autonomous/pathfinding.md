## Paths you didn't draw

A drawn path answers "drive this exact route." Pathfinding answers a different question: **"get from wherever I am to this pose, avoiding the field's obstacles."** PathPlanner computes a route at runtime using an A* variant over a grid of the field, then follows it with the same controller a drawn path uses.

The grid lives in `src/main/deploy/pathplanner/navgrid.json`, generated by the PathPlanner app from the field's static obstacles.

| Use it for | Don't use it for |
|---|---|
| Driving to a fixed scoring or pickup pose from anywhere | A precise autonomous route you will run a hundred times |
| Recovering when an auto starts from the wrong place | Anything where a specific approach angle matters |
| A teleop "take me to the HUB" button | Avoiding other robots, which are not in the grid |

That last row is the important limit. The navgrid holds **static** field elements. Another robot parked in your route is not an obstacle the planner knows about, so pathfinding is a convenience, not a defense.

## Our setup

::source file="src/main/java/frc/robot/Robot.java" from="// enable pathfinding" lines=2

Both lines install the same pathfinder, one in `Drive`'s constructor and one in `Robot`'s. That is finding **F11**: harmless, because the second call replaces an identical object, and confusing, because a reader has to check whether the two differ. Keep the one in `Drive`, where the rest of the PathPlanner wiring lives.

Nothing in our code calls `AutoBuilder.pathfindToPose(...)` yet, and `DriveConstants.pathConstraints` (half speed, 2π rad/s) sits unused waiting for it. The machinery is installed and idle.

## The part worth studying

`LocalADStarAK` is a wrapper around PathPlanner's `LocalADStar` pathfinder that makes it **replay-safe**, and it is the clearest example in our repository of the IO pattern applied to something that isn't a sensor.

::source file="src/main/java/frc/robot/util/LocalADStarAK.java" from="public boolean isNewPathAvailable()" lines=10

Every method follows the same shape:

1. If this is **not** a replay, ask the real pathfinder to do its work.
2. Either way, call `Logger.processInputs`, which records the result during a real run and **replaces it from the log** during a replay.
3. Return the value from the inputs object.

::source file="src/main/java/frc/robot/util/LocalADStarAK.java" from="private static class ADStarIO implements LoggableInputs" lines=4

The inputs class implements `LoggableInputs` by hand instead of using `@AutoLog`, because a list of path points is not a plain field. `toLog` flattens the points into a `double[]`; `fromLog` rebuilds them.

Why go to the trouble? A pathfinder is **non-deterministic in the ways that matter**: it runs on its own schedule, depends on timing, and can return a different route for the same request. Without this wrapper, replaying a match would generate different paths than the robot drove, and the replay would diverge from reality exactly when you most want it to match. With it, the path the robot found is part of the log.

That is a lesson that generalizes: **anything outside your control that influences behavior is an input.** Sensors are the obvious case; a planner, a random number, and the Driver Station are the same problem wearing different clothes.

:::info Using it, if we ever do
```java title="Example: a teleop button that drives to a pose"
controller.y().whileTrue(
    AutoBuilder.pathfindToPose(
        new Pose2d(4.0, 4.0, Rotation2d.fromDegrees(180)),
        DriveConstants.pathConstraints));
```

That command requires the drive (through `AutoBuilder`'s configuration), so releasing the button returns control to the joystick command automatically. Bind it to a button, test it in simulation first, and remember that it will happily drive through another robot.
:::

:::quiz
? What does pathfinding do that a drawn path does not?
+ Generates a route at runtime from wherever the robot is to a goal pose, around static obstacles
- Follows a path more accurately
- Avoids other robots
- Resets odometry automatically
> The navgrid holds the field's static elements only.

? Why isn't pathfinding a defense against other robots?
+ Only static field obstacles are in the navgrid; other robots aren't
- It runs too slowly
- It only works in autonomous
- It ignores the robot's size
> Treat it as a convenience, not collision avoidance.

? What does `LocalADStarAK` add to PathPlanner's pathfinder?
+ It logs the pathfinder's results as inputs and replays them, so a replay follows the same paths the robot found
- It makes pathfinding faster
- It adds obstacle avoidance for robots
- It lets paths be drawn at runtime
> Anything outside your control that changes behavior is an input.

? Why does `ADStarIO` implement `LoggableInputs` by hand instead of using `@AutoLog`?
+ Its data is a list of path points, which needs custom flattening into a `double[]`
- `@AutoLog` doesn't work in the `util` package
- It predates `@AutoLog`
- Pathfinder results are not loggable
> `toLog` and `fromLog` are written explicitly for that reason.

? `Pathfinding.setPathfinder` is called in both `Robot` and `Drive`. What is the consequence?
+ None at runtime, but a reader has to check whether the two calls differ; keep one
- The pathfinder runs twice per loop
- The second call is ignored, so pathfinding is disabled
- Replay breaks
> Finding F11: duplicate setup is a readability bug.

:::
